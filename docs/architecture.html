1. 클래스 작성 규칙

이 엔진의 모든 클래스는 다 만들어졌거나, 아예 안 만들어졌거나 둘 중 하나다. 반쯤 살아 있는 객체를 만들지 않는 것이 규칙 전체의 목적이다.

규칙은 다섯 개다. 이후의 모든 인터페이스가 이 다섯 개의 결과다.

#규칙귀결
1생성자에서 필요한 자원을 전부 만든다init(), open(), start() 같은 2단계 초기화 함수가 없다
2소멸자에서 전부 되돌린다close(), shutdown(), release()를 손으로 짝맞출 일이 없다
3종속성은 생성자로만 받는다setter 주입이 없다. 조립은 아래→위 한 방향(3장)
4성공 여부는 explicit operator bool()로 본다생성자는 던지지 않는다. 실패하면 실패한 객체로 남는다
5공개 함수는 최소한으로, 이름은 일상어로대부분의 클래스가 함수 3~5개다

1.1 생성자가 던지지 않는 이유

이 엔진은 C ABI 경계를 갖고(src/abi/), 예외는 그 경계를 넘을 수 없다. 그래서 생성 실패는 값이다.

// Construction never throws: a failed object stays constructed but unusable, and
// the destructor must still be safe to run on it.
SqliteDataSource store("game.db");

if (!store)
{
    return ErrorCode::DataSourceUnavailable;
}

구현 규약은 둘이다. 실패한 뒤에는 아무 자원도 잡지 않는다(생성자 안에서 부분 성공한 것은 생성자 안에서 되돌린다). 그리고 소멸자는 실패한 객체 위에서도 안전하다. 이 둘을 지키면 호출부는 if (!x) 한 줄로 끝난다.

1.2 이동은 되고 복사는 안 된다

자원을 소유하는 클래스는 전부 move-only다. 두 소유자가 같은 소켓을 닫는 사고를 타입으로 막는다. 이동 연산은 noexcept다 — std::vector에 담기기 때문이다.

2. 전체 구조

다섯 계층이 위에서 아래로만 의존한다. core는 계층이 아니라 모두가 쓰는 재료다.

가장 중요한 경계는 presentation ↔ domain이다. presentation은 바이트를 다루고, domain은 게임 규칙을 다룬다. 소켓·백엔드·엔디안이 domain에 나타나면 자리를 잘못 잡은 것이다.

2.1 core에 들어가는 것

플랫폼도 게임도 모르는 순수 재료만 둔다. 여기 있는 것만 MSVC 없이 Linux에서 새니타이저로 검증할 수 있다는 점이 이 분리의 실질적인 값이다.

3. 조립 순서와 소유

종속성을 생성자로만 받는다는 규칙(1장)이 조립 순서를 강제한다. 아래층부터 만들어 위층 생성자에 넘기고, 마지막에 만들어진 Server가 전부를 소유한다.

그래서 server.registerUsecase(...) 같은 함수가 없다. Usecase 목록은 Server가 만들어지기 전에 완성된다.

1DataSource — SqliteDataSource store("game.db");생성자에서 파일을 열고 WAL을 켜고 statement를 준비한다
▼
2Repository — SessionRepository sessions(store, policy);DataSource 참조를 받는다. 수명은 store가 더 길다
▼
3WorkerRegistry — 워커 목록을 만들면서 스레드가 뜬다몇 개를 어떤 이름으로 둘지는 사용자가 정한다
▼
4Usecase — Holder<IUsecase>::make<LoginUsecase>(sessions, workers.find("storage"))필요한 Repository와 Worker를 여기서 전부 받는다. 실행 중에 더 받지 않는다
▼
5UsecaseRegistry — Usecase 목록을 통째로 넘겨 만든다command 중복이 있으면 operator bool()이 false다
▼
6Server — 나머지 전부를 std::move로 삼킨다생성자에서 listen 소켓을 열고 IO 스레드를 띄운다. 여기서 서버는 이미 돌고 있다
int main()
{
    SqliteDataSource   store("game.db");
    DungeonPolicy      policy;                       // user-defined
    SessionRepository  sessions(store, policy, kMaxSessions);
    WorkerRegistry     workers(makeWorkers());       // threads start here

    if (!store || !sessions || !workers)
    {
        return 1;
    }

    // makeUsecases() returns std::vector<Holder<IUsecase> > - one heap block, no
    // per-object allocation (6.1).
    UsecaseRegistry usecases(makeUsecases(sessions, workers));

    ServerConfig config;
    config.port           = 7777;
    config.io_thread_count = 1;

    Server server(config, std::move(usecases), std::move(workers), sessions);

    if (!server)
    {
        return 1;
    }
    server.wait();                                   // until stop()
    return 0;
}   // ~Server -> ~WorkerRegistry -> ~SessionRepository -> ~SqliteDataSource

소멸은 생성의 역순이고, 그것을 스코프가 보장한다. ~Server가 IO 스레드를 세우고 커넥션을 닫은 다음에야 Worker 스레드가 join되고, 그다음에 DataSource가 닫힌다. 반대로 하면 이미 닫힌 DB를 워커가 만진다.

4. 스레드 모델

스레드는 두 종류뿐이다. IO 스레드는 절대 기다리지 않고, Worker 스레드는 기다려도 된다.

이 경계가 성능 요구(1/60초)의 전부다. 디스크·mmap·파일처럼 시간이 보장되지 않는 일은 전부 Worker로 간다.

4.1 IO 스레드가 하는 일

수신 완료 → 패킷 조립 → 다음 수신 발행 → Codec → Usecase 호출. Usecase가 Worker에 위임하면 그 자리에서 반환되므로 IO 스레드는 계속 돈다. 8명 규모에서는 io_thread_count = 1로 충분하고, 그러면 커넥션 간 경합 자체가 사라진다.

4.2 Worker 스레드가 하는 일

Worker는 일을 맡아 두는 스레드 하나 + 큐 하나다. 엔진은 Worker를 몇 개든 만들 수 있다는 것만 제공하고, 무엇을 맡길지는 정하지 않는다 — 그것은 게임이 정할 일이다.

엔진이 아는 것은 두 가지뿐이다. Worker는 이름으로 찾을 수 있고, 일을 맡기면 기다리지 않고 반환된다. 나누는 기준을 굳이 적자면 무엇과 부딪히는가다 — 같은 자원을 만지는 일을 한 Worker에 묶으면 그 자원에 락이 필요 없어지고, 오래 멈출 수 있는 일을 따로 떼면 그 멈춤이 다른 일에 옮지 않는다.

4.3 어디서 실행할지는 Usecase가 정한다

패킷에 그런 필드는 없다. command → Usecase → (inline 또는 Worker) 경로는 전부 서버가 결정하며, 클라이언트 입력이 관여하지 않는다.

이렇게 하면이렇게 실행된다고르는 기준
Usecase가 직접 계산IO 스레드에서 그대로 (inline)메모리 조회·계산처럼 측정으로 짧다고 확인된 일
주입받은 Worker에 post()Worker 스레드에서 나중에디스크·파일·mmap 등 시간이 보장되지 않는 일
엔진은 이것을 강제하지 않는다. inline에서 DataSource를 타면 IO 스레드가 디스크에서 멈추고, 그 스레드가 맡은 모든 세션이 같이 멈춘다. 함수가 얼마나 걸리는지는 사용자만 측정할 수 있으므로 가이드로 둔다.

5.3 분할된 패킷은 Repository가 모은다

64 KiB를 넘는 데이터는 조각으로 나뉘어 온다. 엔진은 조각을 모으지 않는다. 조각 그대로 Usecase에 올리고, Usecase는 받은 조각을 Repository에 계속 넘긴다. 완성 여부를 아는 것도 완성본을 돌려주는 것도 Repository다.

IoLoop ──► Codec ──► Usecase ──조각──► Repository (사용자 정의)
                        ▲                  │
                        └── 완성본 또는 ────┘
                            "아직 덜 왔다"

엔진이 조립하지 않는 이유는 하나다 — 완성본을 어디에 얼마나 담아 둘지가 게임마다 다르다. 엔진이 하려면 세션마다 미완성 버퍼를 들고 있어야 하는데, 그 상한과 만료 정책이 곧 게임 설계다.

사용자가 지킬 것지키지 않으면
조각을 자기 저장소로 복사해서 들고 있는다execute()가 반환되면 payload 뷰는 무효다 (9.4)
미완성 조각의 개수 상한과 만료 시간을 둔다마지막 조각을 안 보내는 것만으로 메모리가 샌다

조각들은 같은 command로 오고, LastFragment 비트가 선 것이 마지막이다.

5.4 두 흐름을 끝까지 따라가기

지금까지의 조각을 이어 붙인다. 이 서버에서 일어나는 일은 두 가지뿐이고, 둘은 시작점만 다르고 끝은 같다.

[요청·응답]  IoLoop ─► Connection ─► Usecase ─► (Worker 또는 inline) ─► Repository
                                          │                                  │
                                          └──────── 결과 ◄───────────────────┘
                                                     │
[이벤트]     Worker ─► Usecase ─► Repository ─► 결과 ─┤
                                                     ▼
                                        Session.reply() / notify()
                                                     ▼
                                     IStateSink<OutgoingPacket> = Connection
                                                     ▼
                                          SendBuffer ─► IoLoop ─► 소켓

합류점은 Session이다. 요청에서 왔든 틱에서 왔든, 밖으로 나가는 것은 전부 여기를 지난다.

흐름 A — 요청과 응답

// ── IoLoop 스레드 ────────────────────────────────────────────────
ReceivedPacket packet;

while (connection.incoming().takePacket(packet))
{
    // 번호만 발급한다. 슬롯을 잡는 것은 Usecase 의 일이다 (12.2).
    const uint64_t sequence = (session != 0) ? session->nextStateSequence() : 0;

    connection.receiveMore();              // 다음 수신을 로직보다 먼저 건다 (5.1-5)

    IUsecase* usecase = _usecases.find(packet.header->command.get());
    ...
    usecase->execute(Request(session, connection, info, packet.payload, sequence,
                             packet.header->correlation_id.get()));
}

// ── Usecase — 여기서 실행 자리가 갈린다 ──────────────────────────
void MoveUsecase::execute(const Request& request)
{
    Session& session = *request.session;   // 일반 Usecase 는 인증이 보장된다

    // 순서를 지켜야 하는 변경이므로 여기서 자리를 잡는다 (12.2).
    session.ordered().reserve(request.state_sequence);

    MoveInput input;

    if (!readMoveInput(request.payload, input))
    {
        session.reply(request.correlation_id, makeError(ErrorCode::BadPayload));
        session.ordered().skip(request.state_sequence);   // 실패 경로에서 자리를 비운다
        return;
    }
    // input is a value copy: safe to hand to another thread.
    // request.payload is NOT - it dies when execute() returns (9.4).
    const uint64_t sequence = request.state_sequence;
    const uint32_t corr     = request.correlation_id;

    _worker.post([this, input, sequence, &session, corr]
    {
        // 순서를 지켜야 하는 변경은 Repository 를 직접 부르지 않는다.
        // 번호와 함께 넣으면 SequenceStateStream 이 차례가 될 때 흘려 준다.
        session.ordered().set(sequence, computeDelta(input, corr));
    });
}

// 커널이 채울 자리를 내준다. 앞당김은 오직 여기서만 일어난다.
ByteSpan ReceiveBuffer::spaceToFill()
{
    if (_capacity - _limit < kMinPostBytes && _head > 0)
    {
        // Safe here and only here: no IO is in flight and no payload view is alive.
        memmove(_data, _data + _head, _limit - _head);
        _limit -= _head;
        _head   = 0;
    }
    return ByteSpan(_data + _limit, _capacity - _limit);
}

void ReceiveBuffer::filled(size_t bytes)
{
    _limit += bytes;      // 커널이 쓴 만큼 파싱 한계선을 민다
}

// 헤더 + payload 가 다 모였을 때만 true. 아니면 그대로 두고 false.
bool ReceiveBuffer::takePacket(ReceivedPacket& out)
{
    if (_limit - _head < kHeaderSize)
    {
        return false;     // 헤더가 덜 왔다
    }

    // 정렬 요구가 1이라 이 캐스팅이 안전하다 (9.1).
    const PacketHeader* header = reinterpret_cast<const PacketHeader*>(_data + _head);
    const size_t        length = header->payload_length.get();

    if (_limit - _head < kHeaderSize + length)
    {
        return false;     // payload 가 덜 왔다
    }

    out.header  = header;
    out.payload = ByteView(_data + _head + kHeaderSize, length);
    _head      += kHeaderSize + length;
    return true;
}
이 버퍼의 불변식은 하나다 — 커널이 쓰는 구간과 파싱하는 구간은 절대 겹치지 않는다. 
[0 ......... _head ......... _limit ......... _capacity)
              └── 파싱 구간 ──┘└── 커널이 쓰는 구간 ──┘
                (뷰가 여기를 가리킨다)   (submitReceive 로 맡긴 자리)

{

    // push 를 먼저 하고 CAS 한다. 순서를 뒤집으면 lost wakeup 이다 (7.1).
    if (!_send_state.compare_exchange_strong(expected, SendState::Sending))

    {
        _send_state.store(SendState::Idle);
    }
}

6.1 Holder<Base> — 힙 없이 담는 다형 컨테이너 core/kiotty_holder.hpp

std::vector<std::unique_ptr<IUsecase> >는 힙을 두 겹으로 쓴다. 벡터가 포인터 배열용으로 한 덩이, 그리고 각 unique_ptr이 객체마다 따로 한 덩이. 객체들이 힙 여기저기에 흩어지므로 순회는 포인터 추적이 되고, 메모리는 조각난다.

Holder는 파생 객체를 자기 안에 담는다. 크기 상한은 base 클래스가 상수로 선언하고, 그것을 넘는 파생 클래스는 컴파일이 실패한다. 상한이 컴파일 타임에 정해지므로 sizeof(Holder<Base>)가 확정되고, std::vector<Holder<Base> >는 힙 덩이 하나에 객체들이 연속으로 놓인다.

소유이동 전용이동 전용 (같다)
크기객체마다 꼭 맞게전부 상한 크기로 잡힌다

마지막 줄이 이 선택의 대가다. 파생 클래스 하나가 크면 나머지 전부가 그 크기를 차지한다. 그래서 상한은 넉넉히가 아니라 실제 최대치에 맞춰 잡고, 넘으면 컴파일러가 정확한 숫자를 알려 주므로 그때 올린다. 객체 수가 수만 개가 되는 자리에는 쓰지 않는다 — Usecase·Worker처럼 수가 적고 수명이 프로세스와 같은 것이 대상이다.

이 규칙은 엔진 전체에 적용한다. std::unique_ptr이 필요해 보이는 자리는 먼저 Holder로 되는지 본다. 되지 않는 경우는 하나뿐이다 — 파생 타입의 크기 상한을 컴파일 타임에 정할 수 없을 때(사용자가 런타임에 크기를 정하는 버퍼 등). 그런 것은 애초에 다형 객체가 아니라 Bytes로 다룬다.

6.2 ReceiveBuffer / SendBuffer core/kiotty_connection_buffer.hpp

커넥션 하나가 쓰는 버퍼 둘과 그 항목 타입이 한 헤더에 산다. Connection은 생성되는 순간 이 둘을 자기 것으로 가진다 — 밖에서 받아 오지 않고, 나중에 붙이지도 않는다.

// 꺼낸 패킷 1개. 수신 버퍼를 가리키는 뷰이므로 다음 takePacket() 전까지만 유효하다.
struct ReceivedPacket
{
    const PacketHeader* header;
    ByteView            payload;
    uint64_t            state_sequence;

// 보낼 것 1개. 응답인지 이벤트인지가 여기 붙는다 — 헤더 만드는 규칙이 다르기 때문이다 (5.2).
struct OutgoingPacket

    Bytes      payload;          // 참조 카운트 블록. 브로드캐스트면 여럿이 함께 가리킨다

class ReceiveBuffer

public:
    explicit ReceiveBuffer(size_t capacity);   // 여기서 한 번 잡고 다시는 잡지 않는다
    ~ReceiveBuffer();

    explicit operator bool() const;

    ByteSpan spaceToFill();                    // 소켓이 여기로 직접 읽는다 (복사 0회)
    void     filled(size_t bytes);             // 실제로 들어온 만큼 알린다
    bool     takePacket(ReceivedPacket& out);  // 헤더+payload가 다 모였으면 꺼낸다
};

둘의 속이 다른 이유

바탕왜
ReceiveBuffer선형 버퍼 + 잔여분 앞당김링으로 하면 감싸는 자리에서 헤더 24 byte가 두 조각으로 갈린다. 그러면 헤더를 그 자리에서 읽는 방법(9.1)이 무너진다
SendBufferRingBuffer보낼 항목은 포인터 크기의 작은 값이라 갈릴 것이 없다. 넣고 빼기만 하므로 링이 정확히 맞는다

RingBuffer의 용량은 생성자에서 한 번 정해지고 이후 늘지 않는다. ServerConfig.send_queue_limit이 그 값이다 — 설정에서 오는 값이므로 컴파일 타임 상수로 둘 수 없다.

어느 것을 언제 쓰는가

받는 것흘리는 때쓰는 자리
IStateSink<T>값받는 즉시순서가 이미 맞은 곳 — 그리고 밖으로 나가는 길
SequenceStateSink<T>번호 + 값머리부터 연속으로 찼을 때만여러 Worker로 갈려 순서가 뒤집힐 수 있는 인바운드 델타

밖으로 나가는 길에 새 인터페이스를 만들지 않는다. Connection이 IStateSink<OutgoingPacket>을 구현하고, 그것으로 끝이다. "emit은 절대 블로킹하지 않는다"는 계약이 송신 큐에 필요한 계약과 정확히 같기 때문이다.

IStateSink<Delta>          → 게임 상태 (사용자가 구현)
IStateSink<OutgoingPacket> → 커넥션 송신 큐 (Connection 이 구현)
SequenceStateStream<Delta> → 위의 첫 번째 앞에 끼워 순서를 맞춘다

struct Request
{
    Session*                     session;         // 인증 전이면 0 — IPublicUsecase 만 마주한다 (12.1)
    IStateSink<OutgoingPacket>&  sink;            // 항상 유효. 단 execute() 안에서만 (12.1 ②)
    const ConnectionInfo&        connection;
    ByteView                     payload;         // Codec 입력. execute()가 반환되면 무효가 된다
    uint64_t                     state_sequence;  // 세션이 없으면 0 (8장)
    uint32_t                     correlation_id;  // 응답에 그대로 반사한다
};
// 사용자 코드. 필요한 것은 전부 생성자에서 받는다.
class MoveUsecase : public IUsecase
{
public:
    MoveUsecase(WorldRepository& world, IWorker& world_worker)
        : _world(world)
        , _worker(world_worker)
    {
    }

    uint16_t command() const override { return kCommandMove; }

    void execute(const Request& request) override
    {
        MoveInput input;

        if (!readMoveInput(request.payload, input))   // Codec
        {
            request.session.reply(request.correlation_id, makeError(ErrorCode::BadPayload));
            return;
        }
        // input is a value copy: safe to hand to another thread.
        const uint64_t sequence = request.state_sequence;
        WorldRepository& world  = _world;

        _worker.post([&world, input, sequence] { world.applyMove(input, sequence); });
    }

private:
    WorldRepository& _world;
    IWorker&         _worker;
};

6.7 Worker

엔진이 정하는 것은 Worker가 무엇인지뿐이다. 몇 개를 둘지, 각각 무엇을 맡을지, 이름을 뭐라 할지는 전부 사용자가 정한다(4.2).

class IWorker
{
public:
    static const size_t kHolderSize  = 128;
    static const size_t kHolderAlign = 8;

    virtual ~IWorker() {}

    virtual const char* name() const = 0;
    virtual bool        post(Task task) = 0;   // 블로킹하지 않는다. 큐가 꽉 차면 false
};

// 엔진 기본 구현: 스레드 하나 + 고정 용량 큐 하나.
class ThreadWorker : public IWorker
{
public:
    ThreadWorker(const char* name, size_t queue_capacity);
    ~ThreadWorker();                  // 남은 일을 마치고 join 한다

    explicit operator bool() const;   // 스레드가 떴는가

Task는 std::function이 아니라 고정 크기 인라인 저장소를 가진 타입이다. 람다가 그 안에 들어가면 할당이 0회이고, 넘치면 컴파일이 실패한다 — 런타임에 몰래 할당하지 않는다.

6.8 Session

세션 API는 requirement.md의 세션 유스케이스 S1~S20에서 도출했다. 함수를 먼저 정하고 상황을 끼워 맞추면 필요 없는 함수가 남고 필요한 함수가 빠진다.

세션의 상태는 네 개다

없음 ──로그인(S1)──► 살아있음 ──연결 끊김(S7)──► 고아 ──기한 초과(S11)──► 폐기
                        ▲                          │
                        └───── 재바인딩(S10) ───────┘

즉시 폐기되는 길: 로그아웃(S4) · 정원 초과(S15) · 밀려남(S5) · 서버 종료(S19)

커넥션에 세션이 붙어 있으면 그 커넥션은 인증된 것이다. 그래서 isAuthenticated() 같은 함수가 없다 — 세션 객체를 손에 들고 있다는 사실 자체가 인증이다(S2).

같은 이유로 요청마다 토큰을 싣지 않는다. 토큰은 재바인딩할 때만 쓴다(S10). 매 패킷에 실으면 payload 예산을 계속 갉아먹고, 탈취 표면이 패킷 수만큼 늘어난다.

세션이 커넥션을 붙드는 방법

Connection은 presentation의 타입이다. 그것이 세션으로 새면 Repository가 소켓·버퍼·백엔드를 알게 되고, 그 순간 세션 규칙만 떼어 테스트하는 것이 불가능해진다. 그래서 세션은 값 하나와 sink 하나만 든다.

// core/kiotty_connection_info.hpp
// 이 커넥션이 "무엇인가". POD이고, 복사해서 들고 다닌다. 소켓 타입을 끌고 오지 않는다.
struct ConnectionInfo
{
    uint64_t id;               // 커넥션마다 하나. 닫힌 뒤에도 재사용하지 않는다
    uint64_t opened_at;        // 서버 단조 시각 (us)
    char     remote[46];       // 접속해 온 주소. IPv6 최대 길이 + 종료 문자
    uint16_t remote_port;
};

흘려보내는 쪽은 새로 만들지 않는다. core에 이미 IStateSink가 있고, 그 계약이 정확히 필요한 것이다 — emit은 절대 블로킹하지 않는다(7.1). 값 타입만 바꿔 쓴다.

// Connection 이 이것을 구현한다. 세션은 이 인터페이스만 안다.
class Connection : public IStateSink<OutgoingPacket> { ... };

// 세션이 드는 것
ConnectionInfo             _info;   // 값
IStateSink<OutgoingPacket>* _sink;  // 커넥션이 살아 있는 동안만 유효
흘리는 대상쓰는 것누가 구현하나
게임 상태 변경IStateSink<MyState>사용자
순서를 지켜야 하는 상태 변경SequenceStateSink (8장)엔진
커넥션 밖으로 나가는 것IStateSink<OutgoingPacket>엔진 (Connection)

앞의 둘은 서버 안에서 상태를 옮기고, 마지막 하나가 그 결과를 밖으로 내보낸다. 사용자 상태 흐름이 클라이언트에 닿으려면 어디선가 패킷 항목이 되어 커넥션 큐에 들어가야 하는데, 그 마지막 한 칸이 이것이다.

고아 상태의 표현이 여기서 공짜로 나온다. 커넥션이 끊기면 sink 포인터만 nullptr이 되고 ConnectionInfo는 남는다 — 그것이 곧 고아다. 값과 참조를 나눠 든 덕분이다.

public:

// IOCP 와 io_uring 은 원래 그렇고, epoll 은 이 계약을 흉내 낸다 (5.7).
class IIoLoop
{
public:
    static const size_t kHolderSize  = 256;
    static const size_t kHolderAlign = 8;

    virtual ~IIoLoop() {}

    // 어느 스레드에서 불러도 된다. 자기 스레드로 넘겨야 하는 백엔드는 안에서 넘긴다.
    virtual bool submitAccept(Endpoint& endpoint)      = 0;
    virtual bool submitReceive(Connection& connection) = 0;
    virtual bool submitSend(Connection& connection)    = 0;

Connection이 IIoLoop&를 받는 것은 디스패치하는 쪽을 받는 것과 다르다. 자기 소켓에 IO를 거는 방법은 백엔드만 알고, 커넥션은 그것을 걸어야 한다. 반대로 패킷을 Codec·Registry·Usecase로 넘기는 일은 여전히 커넥션의 일이 아니다 — 그것은 dispatchAll()이 하고, 커넥션은 그 함수의 존재를 모른다.

백엔드 세 개(IocpLoop, EpollLoop, IoUringLoop)가 IIoLoop를 구현하며, 생성자에서 Endpoint와 UsecaseRegistry·SessionRepository를 받는다. 셋의 차이는 submit* 두 함수와 run() 안 세 줄뿐이다(5.7). Server는 이것들을 std::vector<Holder<IIoLoop> >로 들고 있다.

Connection은 무엇을 종속성으로 받지 않는가

디스패치하는 쪽을 받지 않는다. 패킷을 꺼내 Codec·Registry·Usecase로 넘기는 것은 IIoLoop의 일이지 Connection의 일이 아니다. Connection이 그것을 들고 있으면 커넥션 하나가 서버 전체를 아는 셈이 되고, 그 순간 커넥션만 떼어 테스트할 수 없게 된다. Connection이 아는 것은 소켓 하나와 자기 버퍼 둘뿐이다.

waiting_limit — 대기열 길이

접속 요청이 들어오면 커널이 먼저 받아 두고, 서버가 accept()로 하나씩 꺼내 간다. 아직 꺼내 가지 않은 것들이 줄 서 있는 곳의 길이가 이 값이다. 줄이 꽉 찬 상태에서 새 접속이 오면 커널이 거절한다.

이 값이 문제가 되는 경우는 하나뿐이다 — 접속이 몰려 들어오는 속도가 accept()로 꺼내는 속도보다 빠를 때. 동시 8명 규모에서는 일어나지 않으므로 64로 두고 잊는다. 튜닝 대상이 아니라 "여기 줄이 있다"는 사실만 알면 되는 값이라서 ServerConfig에 남겨는 두되 기본값을 쓴다.

7. 커넥션 상태

커넥션은 상태 세 개를 각각 하나씩 가진다 — 받는 중 어디까지 왔나, 보내는 중인가, 살아 있나.

"어느 Worker에서 실행 중인가"는 상태가 아니다. 커넥션은 로직의 완료를 기다리지 않으므로 기다림을 나타내는 상태 자체가 필요 없다.

enum class RecvStep
{
    ReadingHeader,   // 24 byte가 모일 때까지
    ReadingPayload,  // payload_length 만큼 모일 때까지
    Dispatching,     // 패킷 1개 완성. 머무는 시간은 0이다
};

enum class SendState
{
    Idle,            // 보낼 것이 없어 체인이 멈췄다. 큐에 넣은 쪽이 시동을 건다
    Sending,         // 전송 중. 다른 스레드는 발행하면 안 된다
};

enum class LifeState
{
    Active,
    Closing,         // 새 작업 발행 금지. pending io가 0이 될 때까지 대기
    Closed,

7.1 전이 규칙

규칙지키지 않으면
다음 수신은 Dispatching으로 넘어가기 전에 발행한다로직 시간만큼 수신 창이 빈다. 요구사항 2·4를 못 지킨다
소켓당 수신 1개, 송신 1개까지. 같은 방향으로 2개는 금지같은 소켓에 두 전송이 겹쳐 바이트가 섞인다
생산자는 큐에 넣고 나서 Idle → Sending CAS순서를 뒤집으면 넣은 것을 아무도 못 보는 lost wakeup
완료 핸들러는 먼저 Sending → Idle로 되돌리고 큐를 한 번 더 본다같은 이유로 마지막 항목이 큐에 남는다
Closing에서는 새 io를 발행하지 않고 pending이 0이 되기를 기다린다커널이 아직 참조 중인 버퍼를 해제한다

7.2 커넥션과 세션은 수명이 다르다

연결 종료 ──► Connection: Closing → Closed → 해제
                     │
                     └──► SessionRepository.detach(connection)
                              │
                              ├── policy.orphanLifetimeMs() == 0  ──► 즉시 폐기
                              └── > 0 ──► 고아 상태로 보관 (송신 큐는 버린다)
                                            ├── 기한 내 rebind(token) ──► 새 커넥션에 붙는다
                                            └── 기한 초과 ──► sweep() 이 폐기한다

7.3 requestSend()가 감추는 것

"누가 실제로 소켓에 쓰는가"가 백엔드마다 다르다. 호출부는 어느 백엔드에서도 queue.push() → requestSend() 두 줄로 동일하다.

쓰는 주체깨우는 방법왜
IOCP아무 스레드나필요 없음작업이 발행 시점에 자기완결적이고, 소켓이 스레드가 아니라 포트에 등록된다
epollsend()는 루프 스레드만epoll_ctl로 EPOLLOUT armepoll_ctl은 스레드 안전하고, 준비된 이벤트를 추가하면 블록된 epoll_wait를 그 자리에서 깨운다. 따로 깨울 필요가 없다
io_uringring 소유 스레드msg_ring 또는 eventfdSQ ring이 스레드 안전하지 않다

IOCP에서는 CAS에 이긴 스레드가 그 자리에서 WSASend를 발행한다. inline Usecase면 IO 스레드가 발행하게 되는데 이것이 최적이다 — 스레드 홉이 0이다. io_uring은 IO 스레드마다 ring 하나를 두고 세션을 ring에 고정한다. 그러면 제출이 ring당 단일 스레드가 되어 락이 사라지고 구조가 epoll과 같아진다.

8. 순서 보장

클라이언트는 절대값을 보내지 못하고 델타만 보낸다. 그 귀결로 인바운드 요청은 하나도 누락되면 안 되고, 순서도 지켜져야 한다 — 델타는 하나만 건너뛰어도 상태가 영구히 어긋난다.

역전이 생기는 지점은 하나뿐이다. 11번이 Worker A로, 12번이 Worker B로 가서 B가 먼저 끝나는 경우다.

8.1 왜 절대값을 막는가

클라이언트가 절대값을 보내는 순간 서버 상태가 클라이언트 입력으로 결정된다. 조작 표면이 그대로 열린다. 클라이언트는 의도를 보내고 서버가 결과를 계산한다. 델타 값 자체도 서버가 검증한다. 반대 방향(서버 → 클라 이벤트)은 서버가 권한을 가지므로 절대값 스냅샷을 보내도 된다.

엔진sweep(now)주기적으로. 영영 안 차는 자리를 잡아낸다
슬롯은 순서 보장이 필요한 Usecase만 잡는다. 엔진이 모든 패킷에 자동으로 잡으면, 조회처럼 set()을 부를 일이 없는 요청이 슬롯을 비우지 않은 채 남아 그 세션의 모든 델타를 뒤에서 멈춰 세운다(12.2 ③). 잡은 쪽이 비우는 책임도 진다 — reserve()를 불렀으면 모든 실패 경로에서 skip()을 부른다. 
reserve(11) reserve(12) reserve(13)
   │           │           │
   ▼           ▼           ▼
 [ 11 ]  →  [ 12 ]  →  [ 13 ]        머리부터 연속으로 찬 것만 반영하고 멈춘다
   비었음      찼음        찼음
   └─ 여기서 멈춘다. 12·13은 대기 (유실이 아니라 늦은 것이다)

set(11, delta) 가 오면 ─► 11 · 12 · 13 이 한 번에 순서대로 target 으로 흘러간다
                          target 은 IStateSink<Delta> — 게임 상태다

슬롯을 미리 잡아 두는 것이 핵심이다. "11이 올지 안 올지 모르는 대기"가 "등록된 11번 슬롯이 아직 안 찼다"로 바뀌어 타임아웃 판단이 명확해지고, 버퍼 크기가 세션당 in-flight 요청 수로 자동 한정된다.

워커가 죽어 슬롯이 영영 안 차면 조용히 건너뛰지 않는다. 델타는 건너뛸 수 없으므로 세션 오류로 취급하고 스냅샷 재동기화를 유도한다. 조용한 skip은 어긋난 상태를 정상인 척 유지시킬 뿐이다.

8.3 엔진이 책임지지 않는 것

어떤 Worker를 쓸지는 Usecase의 소유다. 따라서 세션당 순서 보장 자체는 엔진 사용자 책임이고, 엔진은 state_sequence와 위 모듈이라는 재료만 제공한다. 사용자가 지켜야 할 계약은 하나다.

서로 다른 Worker로 갈 수 있는 상태 변경 연산은, Repository의 임계 구역 안에서 자기 사전조건을 검사한다. Repository의 락은 원자성을 보장할 뿐 순서를 보장하지 않는다. 검사 없이 항상 성공하는 연산(누산, 대입)이나 여러 Repository에 걸친 불변식은 SequenceStateStream으로 직렬화해야 한다.

9. 버퍼와 복사 예산

목표는 소켓 수신 버퍼 → Codec 입력까지 복사 0회다. 그것을 가능하게 하는 것이 와이어 구조체 제약이다.

9.1 헤더를 캐스팅해도 안전한 이유

헤더의 모든 필드를 LittleEndian<T>로 선언하고 원시 바이트를 private으로 감춘다. 그러면 변환을 거치지 않고 필드를 읽는 방법이 존재하지 않게 된다.

struct PacketHeader : WireStruct<PacketHeader, 24>
{
    LittleEndian<uint32_t> magic;
    LittleEndian<uint32_t> correlation_id;
    LittleEndian<uint64_t> timestamp;        // 서버 단조 시각 (us)
    LittleEndian<uint16_t> command;
    LittleEndian<uint16_t> flags;            // 이벤트 · 분할 · 마지막 조각 · 압축
    LittleEndian<uint16_t> version;          // major 1 byte + minor 1 byte
    LittleEndian<uint16_t> payload_length;   // <= 65535
};

부작용이 본론이다. 구조체의 정렬 요구가 1이 되어, 수신 버퍼의 임의 위치를 const PacketHeader*로 캐스팅해도 미정렬 접근 UB가 없다. WireStruct<T, N>는 sizeof(T) == N과 standard layout 여부를 컴파일 타임에 검사한다. 와이어 구조체에 bool·enum·포인터·size_t는 쓰지 않는다 — 플랫폼마다 크기가 다르다.

9.2 수신 버퍼

커넥션마다 선형 버퍼 하나를 두고 꼬리에 직접 읽는다. 머리부터 패킷을 꺼내고, 꼬리가 끝에 닿으면 남은 조각만 앞으로 당긴다.

[ 처리 끝난 부분 ][ 아직 안 끝난 패킷 조각 ][ 빈 공간 ← 여기로 직접 읽는다 ]
                  └───── 꼬리가 끝에 닿을 때만 앞으로 당긴다 ─────┘

흔한 경우 복사는 0회다. 앞당김은 덜 도착한 패킷이 있을 때만 일어나고, 그 크기는 최대 한 패킷이다. 링 버퍼를 쓰지 않는 이유는 감싸는 지점에서 헤더가 두 조각으로 갈리기 때문이다 — 그러면 캐스팅이 불가능해져 9.1의 이점이 사라진다.

9.3 송신 버퍼

헤더 24 byte와 payload를 붙이지 않는다. 두 조각을 한 번의 호출로 보낸다(WSASend / writev는 조각 배열을 받는다). 붙이려면 payload 전체를 복사해야 하는데, 그 복사가 정확히 요구사항 11번이 없애려는 것이다.

보낼 것: [헤더 24B] + [payload]
         └ 세션의 작은 헤더 슬롯      └ Bytes 블록 (참조 카운트)

브로드캐스트: 직렬화 1회 → 같은 Bytes 블록을 N개 세션이 함께 가리킨다
              → 마지막 전송이 끝나면 블록이 풀로 돌아간다

9.4 payload 뷰의 수명

Request.payload는 수신 버퍼를 가리키는 뷰이고, execute()가 반환되면 무효가 된다. Worker로 넘길 값은 execute() 안에서 값으로 복사되어 있어야 한다. 이 규칙 하나가 zero-copy와 수명 안전을 동시에 성립시킨다.

9.5 ByteView와 Bytes core/kiotty_bytes.hpp

복사 예산은 결국 이 두 타입으로 표현된다. 가리키기만 하는 것과 가지고 있는 것을 타입으로 갈라 놓아, 실수로 죽은 버퍼를 붙들고 있는 코드가 눈에 띄게 만든다.

// 남의 버퍼 한 조각을 가리키는 읽기 전용 뷰. 소유하지 않는다.
// C++17의 string_view 를 못 쓰므로(C++11/14 타깃) 같은 것을 직접 둔다.
class ByteView
{
public:
    ByteView()
        : _data(nullptr)
        , _size(0)
    {
    }

    ByteView(const uint8_t* data, size_t size)
        : _data(data)
        , _size(size)
    {
    }

    const uint8_t* data() const { return _data; }
    size_t         size() const { return _size; }

    explicit operator bool() const { return _data != nullptr; }

    // Contract: the range must be inside this view. Violating it is a caller bug.
    ByteView slice(size_t offset, size_t count) const
    {
        assert(offset + count <= _size && "slice() out of range");
        return ByteView(_data + offset, count);
    }

private:
    const uint8_t* _data;
    size_t         _size;
};

구현할 것이 이게 전부다. 포인터 하나와 길이 하나, 16 byte짜리 값이다. 특수 멤버를 아무것도 쓰지 않는다(rule of zero) — 소유하는 것이 없으니 복사·이동·소멸에 할 일이 없다. 그래서 인자로 값으로 넘기는 것이 참조로 넘기는 것보다 싸다.

ByteViewBytes
소유없다. 남의 것을 가리킨다있다. 블록 풀에서 얻어 참조 카운트로 나눠 쓴다
복사포인터+길이 복사 (16 byte)카운트만 올린다. 바이트는 그대로
수명가리키는 버퍼보다 먼저 죽어야 한다마지막 소유자가 사라질 때 풀로 돌아간다
쓰는 곳수신 — 소켓 버퍼를 그대로 읽는다송신 — 여러 세션이 한 payload를 나눠 가진다

이 둘의 경계가 곧 복사가 일어나는 지점이다. 수신은 끝까지 ByteView로 가고(복사 0회), 밖으로 나갈 것을 만들 때 처음 Bytes가 된다. Worker로 넘기거나 나중에 쓰려면 반드시 Bytes로 옮겨야 한다 — ByteView인 채로 넘기면 9.4의 규칙을 어기는 것이다.

// BAD - the view dies with execute(); the worker reads freed memory.
_worker.post([view] { store(view); });

// GOOD - copy into an owned block first.
Bytes owned = Bytes::copyOf(_pool, view);
_worker.post([owned] { store(owned); });

10. TLS 빌드 스위치

TLS는 런타임 플래그가 아니라 빌드 옵션이다. OFF로 빌드하면 TLS 종속성이 바이너리에 아예 들어가지 않는다.

Socket과 TlsSocket은 같은 함수 네 개를 갖는다. IoLoop는 둘 중 무엇을 쓰는지 모른다.

# CMake
option(KIOTTY_ENABLE_TLS "Link TLS backend" OFF)
#if defined(KIOTTY_ENABLE_TLS)
typedef TlsSocket ConnectionSocket;
#else
typedef Socket    ConnectionSocket;
#endif

핸드셰이크는 TlsSocket의 읽기·쓰기 안에서 진행된다. 그동안 operator bool()은 true(소켓은 살아 있다)이고, 핸드셰이크가 실패하면 읽기가 오류를 돌려주어 커넥션이 Closing으로 간다. 즉 IoLoop의 상태 기계는 TLS 유무와 무관하게 동일하다.

11. 클라이언트 수신 구조

클라이언트는 구현 범위 밖이다. 그런데도 이 장이 있는 이유는 프로토콜이 클라이언트를 구현 가능하게 만들어야 하기 때문이다. 서버가 응답과 이벤트를 같은 소켓으로 보내므로 클라이언트는 이 둘을 스스로 갈라야 하고, 가를 수 있으려면 헤더가 그 정보를 주어야 한다.

11.1 flags의 Event 비트

비트이름뜻
0Event1이면 서버가 스스로 보낸 이벤트다. 0이면 요청이거나 그 응답이다
1Fragmented분할된 데이터의 한 조각이다
2LastFragment분할된 것 중 마지막 조각이다
3Compressedpayload가 압축되어 있다

correlation_id만으로는 구분할 수 없다. 요청 번호는 클라가, 이벤트 번호는 서버가 각각 발급하므로 두 숫자 공간이 겹친다 — 같은 값 7이 내 요청의 번호이면서 동시에 서버 이벤트의 번호일 수 있다. 이 비트가 그 모호함을 없앤다.

11.2 요청을 동기 함수로 쓰려면 수신 스레드가 필요하다

요청을 보낸 스레드가 직접 소켓을 읽으면, 그 자리에 도착하는 것이 자기 응답이라는 보장이 없다. 이벤트가 먼저 오면 그것을 처리하느라 응답이 늦어지고, 버리면 이벤트가 유실된다. 수신을 한 스레드로 모으고 거기서 가르는 것이 유일한 구조다.

규칙지키지 않으면

12. 사례를 통한 구조 간 흐름 분석

앞 장까지의 구조에 실제 요청 네 개를 통과시켜 본다. 목적은 설명이 아니라 검증이다 — 흐름이 막히는 곳, 인터페이스가 모자란 곳을 찾는 것이 이 장의 성과다.

네 사례 모두에서 문제가 나왔다. 대부분은 고쳤고, 두 개는 결정이 필요하다. 결과는 12.5에 모았다.

드러난 것 ① Request에 세션이 없을 수 있다

기존 Request는 Session&를 들고 있었다. 로그인 시점에는 그것이 존재하지 않는다. 그리고 응답은 보내야 한다.

struct Request
{
    Session*                     session;         // 인증 전이면 0 (IPublicUsecase 만 해당)
    IStateSink<OutgoingPacket>&  sink;            // 항상 유효 — 단, execute() 안에서만
    const ConnectionInfo&        connection;
    ByteView                     payload;
    uint64_t                     state_sequence;  // 세션이 없으면 0
    uint32_t                     correlation_id;
};

일반 IUsecase에서는 엔진이 인증을 보장하므로 session이 항상 non-null이다. IPublicUsecase만 null을 마주한다 — 상속한 타입이 곧 그 표시다.

드러난 것 ② 인증 전 커넥션에는 수명 보호막이 없다 결정 필요

인증된 뒤에는 Session이 방패가 된다. Worker가 session.reply()를 부르는 동안 detach()가 같은 락에서 기다리므로 커넥션이 그 사이에 사라질 수 없다(5.4).

로그인 응답에는 그 방패가 없다. Worker가 DB를 보는 동안 클라이언트가 끊으면, 응답할 때 sink 참조는 이미 죽은 Connection을 가리킨다.

// 지금 구조에서 이것이 위험하다 — sink 는 execute() 가 반환되면 보장이 끝난다.
_worker.post([&sink, corr] { ... sink.emit(item); });   // BAD

제안하는 해결은 참조를 아예 들지 않는 것이다. Worker는 connection_id(값)만 캡처하고, 보낼 때 IoLoop가 소유한 표에 물어본다.

// IoLoop 가 소유한다. 살아 있는 커넥션만 들어 있다.
class ConnectionTable
{
public:
    bool send(uint64_t connection_id, OutgoingPacket item);   // 없으면 false. 그것이 S8이다
};

_worker.post([this, connection_id, corr] { _connections.send(connection_id, item); });   // GOOD

이렇게 하면 Session에서도 sink 포인터와 락이 사라지고 connection_id 하나만 남는다 — 인증 전과 후가 같은 경로가 된다. 다만 매 송신마다 표를 한 번 찾는 비용이 붙는다(8명 규모에서는 측정되지 않을 것이다).

드러난 것 ③ 슬롯을 IoLoop가 잡으면 세션이 굳는다

기존 설계는 IoLoop가 번호를 매기는 자리에서 모든 패킷에 reserve()를 걸었다. 읽기 요청은 set()을 부를 일이 없으므로 그 슬롯은 영영 안 찬다. 누군가 skip()을 불러 줘야 머리가 지나가는데, 그것을 잊으면 그 세션의 모든 델타가 뒤에서 멈춘다. 잊기 쉬운 자리에 치명적인 결과를 둔 셈이다.

고친 규칙은 하나다.

IoLoop는 번호만 발급한다. reserve()는 순서 보장이 필요한 Usecase가 직접 부른다.

요구사항 §7이 슬롯 예약에서 얻으려던 것("11이 올지 안 올지 모르는 대기"를 "등록된 11번이 아직 안 찼다"로 바꿔 타임아웃 판단을 명확히 하기)은 그대로 유지된다. 등록하는 주체만 바뀐다. 그리고 읽기 요청은 순서 보장 기구에 아예 등장하지 않는다 — 등장하지 않는 것은 굳을 수도 없다.

12.3 사례 3 — 스킬 포인트 찍기 요청/응답 · 수정 후 새 값 반환

이 사례가 가장 많은 것을 드러냈다. 델타를 반영하고 반영된 결과를 응답으로 돌려줘야 하기 때문이다.

드러난 것 ④ set() 직후에는 값을 읽을 수 없다

set(seq, delta)는 즉시 반영하지 않는다. 앞 번호가 아직 안 왔으면 기다린다(8.2). 그러니 set() 바로 다음 줄에서 새 값을 읽으면 반영 전 값을 읽는다.

// BAD - 아직 반영되지 않았다. 앞 번호를 기다리는 중일 수 있다.
session.ordered().set(sequence, delta);
session.reply(corr, encode(_skills.pointsOf(skill_id)));   // 옛 값

응답은 반영이 끝나는 자리에서 보낸다. 그 자리는 SequenceStateStream의 도착지, 즉 사용자가 구현한 IStateSink<Delta>다. 그래서 델타가 응답에 필요한 것을 함께 싣고 간다.

// 델타는 "무엇을 바꿀지"와 "누구에게 알릴지"를 함께 들고 간다.
struct SkillDelta
{
    uint64_t session_id;
    uint32_t correlation_id;
    uint16_t skill_id;
    int16_t  points;         // 절대값이 아니라 증분 (요구 9)
};

// Usecase — 계산만 하고 넣는다. 응답하지 않는다.
void SkillUsecase::execute(const Request& request)
{
    request.session->ordered().reserve(request.state_sequence);   // 여기서 잡는다 (12.2)

    _worker.post([...]
    {
        SkillDelta delta = ...;
        session.ordered().set(sequence, delta);   // 차례가 되면 아래가 불린다
    });
}

// 사용자가 구현한 도착지 — 반영과 응답이 같은 자리에서 일어난다.
bool SkillState::emit(SkillDelta delta) override
{
    const int32_t new_points = _skills.add(delta.skill_id, delta.points);

    _sessions.send(delta.session_id, delta.correlation_id, encode(new_points));
    return true;
}

이 구조가 성립한다는 것이 사례 3의 결론이다. 다만 직관적이지 않다 — 응답을 Usecase가 아니라 상태 도착지가 보낸다. "수정하고 새 값을 돌려주는" 모든 Usecase가 이 모양이 되므로, 클라이언트 가이드와 예제에 이것을 못 박아야 한다.

드러난 것 ⑤ 실패한 요청은 반드시 skip()해야 한다

스킬 포인트가 모자라 거절되면 set()이 불리지 않는다. 그 자리를 비워 주지 않으면 뒤의 모든 델타가 멈춘다. reserve()를 부른 Usecase는 모든 실패 경로에서 skip()을 불러야 한다 — 12.2의 규칙이 이 부담을 순서 보장이 필요한 Usecase로만 한정해 준다.

  • Oldest — 사건이 사라진다. 틀렸다
  • Never — 큐가 넘치면 연결을 끊는다. 이벤트 때문에 끊는 것은 과하다

13.1 범위 밖과 이후 계획

  • heartbeat — 클라이언트가 범위 밖이라 도입하지 않는다. 알려진 한계: 무선 단절처럼 아무 신호 없이 끊기면 TCP 재전송 타임아웃까지 감지되지 않는다. 정상 종료(FIN)와 크래시(RST)는 즉시 감지된다.
  • rate limiting — 도입 전까지 요구사항 4번은 "정상 클라이언트 전제"에서만 성립한다.
  • UDP — 전용 루프를 따로 두지 않는다. UDP 소켓도 같은 IoLoop에 등록되고 완료 처리만 달라진다.
  • room, cache, metrics, clock — 아래 미결정이 정리된 뒤 착수한다.
  • 클라이언트 코드 작성 가이드(docs/client_guide.md) — 설계가 모두 확정된 뒤에 만든다. 클라이언트는 이 가이드를 보고 통신 코드를 생성해 지금 쓰고 있는 MockServer를 대체한다. 담아야 할 것은 Usecase 목록 전부(command 번호·요청/응답 payload·실패 코드), 동기 요청 함수 Response doUsecase(Client&, const Request&), 이벤트 스트림 Stream<GameEvent>(Client를 종속성으로 받는다), 그리고 11장의 수신 분기와 재연결 절차다.
