AES-256-GCM

이 엔진의 Cryptor(저장 데이터·보관 토큰의 양방향 암복호화)가 쓰는 방식. 이 문서만 읽고 끝낼 수 있게 썼다.

AES는 16 byte 한 덩어리를 키로 뒤섞는 함수다. 그것만으로는 긴 데이터를 다룰 수 없다.

운용 모드는 16 byte 함수를 긴 데이터에 반복 적용하는 규칙이다. GCM은 그 규칙 중 하나로, 암호화하면서 변조 감지 태그를 같이 만든다.

이 엔진에서 필요한 것은 셋이다 — 되돌릴 수 있을 것, 저장소가 새도 읽히지 않을 것, 누가 바꿔치기했으면 알아챌 것. 마지막 하나 때문에 GCM이다.

1. AES — 16 byte 를 뒤섞는 함수

AES는 입력 16 byte와 키(256 bit = 32 byte)를 받아 출력 16 byte를 내놓는 함수다. 키를 모르면 출력에서 입력을 되돌릴 수 없고, 키를 알면 정확히 되돌릴 수 있다.

encryptBlock(key, 16 byte 평문)  → 16 byte 암호문
decryptBlock(key, 16 byte 암호문) → 16 byte 평문

여기까지가 AES의 전부다. 16 byte 하나만 다룬다. "AES로 파일을 암호화한다"는 말은 이 함수를 어떤 규칙으로 반복 적용한다는 뜻이고, 그 규칙이 모드다.

안에서 하는 일은 14라운드(256-bit 키 기준) 동안 같은 네 단계를 반복하는 것이다. 구현할 때 알면 되고, 쓰는 입장에서는 몰라도 된다.

단계하는 일
SubBytes바이트마다 고정된 표(S-box)로 치환
ShiftRows4×4 로 본 16 byte의 행을 옆으로 민다
MixColumns열마다 바이트를 섞는다
AddRoundKey키에서 뽑은 라운드 키와 XOR

2. 왜 모드가 필요한가 — 가장 단순한 방법이 틀리는 이유

제일 먼저 떠오르는 방법: 데이터를 16 byte씩 잘라 각각 encryptBlock. 이것을 ECB 모드라고 하는데, 쓰면 안 된다. 같은 평문 블록은 항상 같은 암호문 블록이 되기 때문에, 암호문만 보고도 "여기와 저기가 같은 내용이다"를 알 수 있다. 이미지를 ECB로 암호화하면 윤곽이 그대로 보이는 유명한 예가 있다.

그래서 제대로 된 모드는 같은 평문이라도 매번 다른 암호문이 나오게 만든다. 그 재료가 nonce(한 번만 쓰는 값)다. 암호화할 때마다 새 nonce를 뽑고, 그것을 암호문과 같이 보관한다. nonce는 비밀이 아니다 — 다만 같은 키로 두 번 쓰면 안 된다.

3. CTR — GCM의 암호화 절반

GCM은 두 부분으로 되어 있다. 암호화는 CTR 모드, 변조 감지는 GHASH. 먼저 CTR.

CTR은 평문을 AES에 넣지 않는다. 카운터를 AES에 넣는다.

nonce (12 byte) + 카운터 (4 byte) = 16 byte 블록

keystream[0] = encryptBlock(key, nonce ‖ 2)
keystream[1] = encryptBlock(key, nonce ‖ 3)
keystream[2] = encryptBlock(key, nonce ‖ 4)
...

암호문 = 평문 XOR keystream

(카운터가 2부터 시작하는 이유는 §5에서 나온다. 1번은 태그용으로 남긴다.)

이렇게 하면 얻는 것.

  • 복호화가 암호화와 같은 코드다. 같은 keystream을 만들어 다시 XOR하면 평문이다. decryptBlock이 필요 없다.
  • 길이 제한이 없다. 16 byte 배수가 아니어도 마지막 keystream의 남는 바이트만 버리면 된다. 패딩이 없다.
  • 같은 평문도 nonce가 다르면 다른 암호문이다.
nonce 재사용이 치명적인 이유가 여기서 보인다. 같은 키·같은 nonce면 keystream이 같다. 두 암호문을 XOR하면 keystream이 사라지고 두 평문의 XOR이 남는다. 그래서 nonce는 암호화할 때마다 BCryptGenRandom / getrandom 에서 12 byte를 새로 뽑는다.

4. 암호화만으로 부족한 이유 — 변조

CTR의 암호문은 평문 XOR keystream이다. 공격자가 키를 몰라도 암호문의 특정 비트를 뒤집으면 평문의 같은 자리 비트가 뒤집힌다. 잔액 필드가 어디 있는지 알면 값을 바꿀 수 있다. 읽지는 못해도 고칠 수는 있는 것이다.

이 엔진에서 Cryptor가 지키는 것은 저장 데이터와 세션 토큰이다. 저장소가 통째로 새는 상황을 가정하는데, 그 상황에서 읽히지 않는 것만으로는 부족하고 고쳐 써넣은 것을 알아채야 한다. 그것이 태그다.

5. GHASH 와 태그 — GCM의 나머지 절반

암호화가 끝나면 암호문 전체를 한 번 더 훑어 16 byte 요약을 만든다. 이 요약이 태그이고, 암호문 뒤에 붙여 보관한다.

H    = encryptBlock(key, 0…0)                   ← 키에서만 나오는 비밀 상수
X    = GHASH(H, 암호문, 길이)                    ← 암호문을 H 로 접어서 16 byte 로
tag  = X XOR encryptBlock(key, nonce ‖ 1)        ← 카운터 1 번이 여기 쓰인다

GHASH는 암호문을 16 byte씩 읽으며 acc = (acc XOR block) · H 를 반복한다. 여기서 ·은 보통 곱셈이 아니라 GF(2128) 곱셈이다 — 128-bit 값을 다항식으로 보고 곱한 뒤 고정 다항식으로 나머지를 취하는 연산. 구현은 시프트와 XOR 뿐이라 30줄 안쪽이다.

핵심은 H를 모르면 태그를 만들 수 없다는 것이다. 공격자가 암호문을 한 비트라도 바꾸면 GHASH 결과가 달라지고, 그 결과를 맞출 H가 없으니 태그를 고칠 수 없다.

복호화 절차

  1. 보관된 nonce·암호문·태그를 읽는다.
  2. 암호문으로 태그를 다시 계산한다.
  3. 계산한 태그와 보관된 태그를 비교한다. 다르면 평문을 내놓지 않고 실패한다.
  4. 같으면 CTR로 복호화한다.

3번 비교는 상수 시간으로 한다 — 첫 바이트에서 틀리든 마지막 바이트에서 틀리든 걸리는 시간이 같게. 앞에서부터 비교하다 멈추면 걸린 시간으로 "몇 바이트까지 맞췄는지"가 샌다.

6. 저장 형식

Cryptor::encrypt가 돌려주는 바이트는 이 셋을 이어 붙인 것이다.

┌──────────┬──────────────────────┬──────────┐
│ nonce 12 │ 암호문 (평문과 같은 길이) │ tag 16   │
└──────────┴──────────────────────┴──────────┘

즉 암호문은 평문보다 항상 28 byte 길다. decrypt는 28 byte보다 짧은 입력을 그 자리에서 거부한다.

7. 알아 두어야 할 한계

한계이 엔진에서의 의미
nonce를 같은 키로 두 번 쓰면 깨진다매번 OS 난수 12 byte. 같은 키로 232번 넘게 쓰면 키를 바꾼다
키가 새면 전부 새는 것이다키는 CipherKey 값으로 서버 시작 시 주입. 저장소에 같이 두지 않는다
직접 구현한 AES는 S-box 표 조회가 캐시 타이밍에 노출된다외부에서 원격으로 측정하기 어려운 저장 데이터 용도라 수용. 네트워크 스트림 암호화(TLS)에는 이 구현을 쓰지 않는다
태그 검증 전의 평문은 신뢰할 수 없다그래서 decrypt는 태그부터 검사하고, 틀리면 평문을 만들지 않는다

8. 이 저장소에서 어떻게 쓰이는가

설계 문서(docs/architecture.html §6.11)가 정한 인터페이스다. 구현 파일은 이 문서를 이해한 뒤 만든다.

// 되돌려야 하는 것 전용 — 저장 데이터, 보관하는 토큰. AES-256.
class Cryptor
{
public:
    explicit Cryptor(const Key& key);
    ~Cryptor();

    explicit operator bool() const;

    Result<ErrorCode, Bytes> encrypt(ByteView plain) const;
    Result<ErrorCode, Bytes> decrypt(ByteView cipher) const;
};

위 문서의 Key는 이 저장소에서 CipherKey(32 byte POD)가 되고, ErrorCode는 영역별 enum 관례를 따라 CryptoCode가 된다. 반환값은 core/kiotty_result.h의 Result와 core/kiotty_bytes.h의 Bytes를 그대로 쓴다.

// src/implementation/core/kiotty_bytes.h — 입력은 ByteView, 출력은 Bytes
class ByteView
{
public:
    ByteView(const uint8_t* data, size_t size);
    const uint8_t* data() const;
    size_t size() const;
    ...
};

class Bytes
{
public:
    Bytes(BlockPool& pool, size_t length);
    ByteSpan writableSpan();
    ByteView view() const;
    ...
};

Bytes는 BlockPool에서만 만들어지므로 Cryptor는 생성자에서 BlockPool&도 함께 받는다. 복호화가 태그 불일치로 실패하면 Result는 CryptoCode::CRYPTO_TAG_MISMATCH를 돌려주고 값은 만들어지지 않는다.
