# 게임 서버 엔진 기획

## 목표

- 던전 앤 파이터와 같은 실시간 게임 동작을 지원하기 위한 서버 엔진을 만든다.
- 서버 엔진만 구현한다. 클라이언트는 구현 범위 밖이다.

## 요구사항

### 기능

1. Request/Response 기능을 지원한다. [Request/Response 모드]
    - 로그인, 로그아웃
    - 영속 상태 변경
2. 클라이언트가 발생시킬 수 있는 Event를 서버에 지속적으로 보내는 Event Sink/Stream 기능을 지원한다. [Stream 모드]
    - 플레이어 입력
3. 서버에서 발생된 Event를 클라이언트에 지속적으로 보내는 Event Sink/Stream 기능을 지원한다. [Stream 모드]
    - 실시간 상태 변경

### 성능

4. 최소 8개의 클라이언트의 동시연결을 지원한다.
    - 연결된 클라이언트로부터 받은 패킷을 해석하여 로직을 처리할 때까지 걸리는 시간이 1/60초 미만이어야 한다.
    - 로직을 처리한 후 연결된 클라이언트에게 패킷을 전달하기까지 걸리는 시간이 1/60초 미만이어야 한다.
    - 서버에서 Event에 대한 패킷을 만든 후, 패킷을 받아야 하는 모든 클라이언트에 전달할 때까지 걸리는 시간이 1/60초 미만이어야 한다.
    - 측정 조건(평균/최대/p99, 부하 수준)은 미정. 아래 [미결정 사항](#미결정-사항) 참고.

### 프로토콜

5. 클라이언트와 서버가 주고 받는 패킷 구조는 아래와 같다. 헤더는 24 byte 고정이다.

    | offset | 크기 | 필드 | 설명 |
    | --- | --- | --- | --- |
    | 0 | 4 | MAGIC | 패킷 시작 식별자 |
    | 4 | 4 | correlation_id | 요청↔응답 대응 및 이벤트 시퀀스 |
    | 8 | 8 | timestamp | 서버 단조 시각 (마이크로초) |
    | 16 | 2 | command | Usecase 식별자 |
    | 18 | 2 | flags | 이벤트 여부 / 압축 / 분할 / 마지막 조각 |
    | 20 | 2 | version | 프로토콜 버전 (major 1 byte + minor 1 byte) |
    | 22 | 2 | payload_length | 최대 65535 |

    - payload는 사용자 정의 byte이며 **최대 64 KiB**이다. 그보다 큰 데이터는 `flags`의 분할 비트를 써서 조각내어 보낸다.
    - `timestamp`가 offset 8에 놓여 8 byte 자연 정렬이 유지된다.
    - 바이트 오더는 **리틀 엔디안**으로 고정한다.
    - `payload_length`는 헤더 파싱 직후, payload 버퍼를 확보하기 **전에** 검증한다. 상한을 넘으면 연결을 종료한다.
    - `correlation_id`의 의미는 방향마다 다르다.
        - 클라 → 서버 요청 : 클라가 발급. **커넥션 안에서만** 유일하면 된다
        - 서버 → 클라 응답 : 요청 값을 그대로 반사한다
        - 서버 → 클라 이벤트 : 세션별 단조 증가 시퀀스. 클라가 유실을 번호 구멍으로 감지할 수 있다
    - `flags`의 비트 정의는 아래와 같다.

        | 비트 | 이름 | 뜻 |
        | --- | --- | --- |
        | 0 | `Event` | 1이면 서버가 스스로 보낸 이벤트다. 0이면 요청이거나 그 응답이다 |
        | 1 | `Fragmented` | 이 패킷이 분할된 데이터의 한 조각이다 |
        | 2 | `LastFragment` | 분할된 것 중 마지막 조각이다 |
        | 3 | `Compressed` | payload가 압축되어 있다 |

    - `Event` 비트가 없으면 클라이언트가 응답과 이벤트를 구분할 수 없다. 둘이 같은 소켓으로 섞여 오는데
      `correlation_id`의 숫자 공간이 서로 겹치기 때문이다(요청 번호는 클라가, 이벤트 번호는 서버가 발급하므로
      같은 값이 양쪽에서 나온다). 이 비트가 클라이언트의 수신 분기를 성립시킨다. [클라이언트 수신 구조](#클라이언트-수신-구조) 참고.
    - 기존 `process_type` 필드는 **제거되었다.** 어떤 Worker에서 실행할지는 서버가 `command → Usecase → Worker` 경로로 결정하며 클라이언트 입력이 관여하지 않는다.

6. 프로토콜 버전을 지원한다.
    - major 불일치는 연결을 거부하고, minor 차이는 허용한다.
    - 핸드셰이크에서 협상하되 헤더에도 매 패킷 유지한다.

### 세션

7. 모든 Usecase는 실행 전에 세션 인증을 통과해야 한다.
    - 인증 검사는 **엔진이 수행한다.** 사용자 로직에 맡기지 않는다.
    - `IPublicUsecase`를 명시적으로 구현한 것만 예외로 허용한다. (로그인, 버전 확인 등)

8. 커넥션 수명과 세션 수명을 분리한다.
    - 커넥션이 끊겨도 세션은 일정 기간 고아(orphaned) 상태로 유지한다.
    - **세션 유효기간을 정하는 로직은 엔진 사용자가 정의한다.** (던전 안 60초, 마을 즉시 정리 등 상황별 차등)
    - 재연결 시도는 클라이언트 책임이다. 엔진은 세션 토큰으로 고아 세션을 새 커넥션에 재바인딩하는 기능만 제공한다.
    - 끊긴 동안 발생한 이벤트는 **보관하지 않는다.** 재연결 후 최신 상태는 사용자가 정의한 스냅샷 조회 Usecase로 받아간다.
    - 세션 토큰은 암호학적 난수여야 한다.

### 세션 유스케이스

세션이 실제로 어떤 상황을 지나는지 전부 적는다. 세션 API는 이 목록에서 도출한다 — 상황을 먼저 세지 않으면
필요 없는 함수가 생기고 필요한 함수가 빠진다.

**세션은 네 가지 상태만 갖는다.** 커넥션에 세션이 붙어 있으면 그 커넥션은 인증된 것이고, 붙어 있지 않으면
인증되지 않은 것이다. 별도의 인증 플래그는 두지 않는다.

```
없음 ──로그인──► 살아있음 ──연결 끊김──► 고아 ──기한 초과──► 폐기
                    ▲                      │
                    └──── 재바인딩 ────────┘
                 (로그아웃 / 정원 초과 / 강제 종료 시 즉시 폐기)
```

**세션 식별 방식.** 요청마다 토큰을 실어 보내지 않는다. 커넥션에 붙은 세션이 곧 그 커넥션의 신원이다.
토큰은 **재바인딩할 때만** 쓴다. 이유는 둘이다 — 매 패킷에 토큰을 실으면 payload 예산을 계속 갉아먹고,
탈취 표면이 패킷 수만큼 늘어난다.

| # | 상황 | 엔진이 하는 일 | 사용자가 정하는 것 |
| --- | --- | --- | --- |
| S1 | 처음 로그인 | 토큰 발급, 세션 생성, 커넥션에 바인딩 | 자격 검증(아이디·비밀번호) |
| S2 | 로그인 이후 요청 | 커넥션에 붙은 세션으로 인증 통과. Usecase 호출 | — |
| S3 | 인증 전에 비공개 Usecase 호출 | `NotAuthenticated` 응답. **연결은 유지** | — |
| S4 | 로그아웃 | 세션 즉시 폐기, 토큰 무효화. 고아로 두지 않는다 | 로그아웃 Usecase 정의 |
| S5 | 같은 계정으로 다른 커넥션에서 로그인 | 정책에 따라 기존 세션을 밀어내거나 새 로그인을 거부 | 어느 쪽인지 |
| S6 | 이미 인증된 커넥션에서 다시 로그인 | `AlreadyAuthenticated` 응답. 연결 유지 | — |
| S7 | 연결이 끊김 | 커넥션 정리, 세션은 고아로. 송신 큐는 버린다 | 고아 유지 기간 |
| S8 | 응답을 보내려는데 이미 끊김 | 응답을 버린다. 재전송하지 않는다 | — |
| S9 | 이벤트 대상인데 이미 끊김 | 아무 일도 하지 않는다(no-op). 보관하지 않는다 | — |
| S10 | 기한 내 재접속 + 토큰 제시 | 고아 세션을 새 커넥션에 재바인딩 | 재바인딩 후 스냅샷 Usecase |
| S11 | 기한 초과 후 토큰 제시 | `SessionUnavailable` 응답. 재로그인을 유도한다 | — |
| S12 | 무효한 토큰(로그아웃 후 / 조작) | S11과 **같은 응답**. 구분은 서버 로그에만 남긴다 | — |
| S13 | 아직 커넥션이 붙어 있는 세션에 재바인딩 시도 | 기존 커넥션을 닫고 새 커넥션에 붙인다 | — |
| S14 | 두 커넥션이 같은 토큰으로 동시에 재바인딩 | 하나만 성공한다. 나머지는 `SessionUnavailable` | — |
| S15 | 세션 정원 초과 | `TooManySessions` 응답 후 연결 종료 | 정원 값 |
| S16 | Worker가 늦게 끝났는데 세션이 이미 없음 | 결과를 버린다. sink가 no-op이 된다 | — |
| S17 | 송신 큐 상한 초과(`Never` 항목) | 연결 종료 → S7로 간다 | 큐 상한 |
| S18 | 순서 슬롯 타임아웃(설계 가이드라인 7번) | 세션 오류로 표시. 재동기화를 유도한다 | 타임아웃 값 |
| S19 | 서버 종료 | 모든 세션 폐기. 고아도 남기지 않는다 | — |
| S20 | 서버 재시작 후 옛 토큰 제시 | S11과 같다. 세션은 메모리에만 존재한다 | 세션 영속화 여부(현재 안 함) |

**S12를 S11과 같은 응답으로 두는 이유.** 만료와 위조를 구분해 알려주면 "그 토큰이 존재는 했는가"가
새어 나간다. 클라이언트가 할 일은 어느 쪽이든 재로그인이므로 구분할 실익도 없다.

**S13이 예외처럼 보이지만 정상 경로다.** heartbeat가 없으므로(범위 밖) 무선 단절은 TCP 재전송
타임아웃까지 감지되지 않는다. 그동안 클라이언트는 이미 재접속해 있다. 즉 **살아 있어 보이는 옛 커넥션과
새 커넥션이 겹치는 구간이 실제로 자주 생긴다.** 새 커넥션을 우선한다.

**S8은 되짚어 볼 여지가 있다.** 요청은 반영되었는데 응답만 유실된 상태다. 클라이언트가 같은 요청을 다시
보내면 델타가 두 번 적용된다(요구사항 9번의 귀결). 아래 [미결정 사항](#미결정-사항) 6번 참고.

### 상태

9. 클라이언트 요청으로 서버 상태를 바꿀 때 **절대값 대입을 허용하지 않는다.** 누적/델타만 허용한다.
    - 클라이언트가 절대값을 보내는 순간 서버 상태가 클라이언트 입력으로 결정된다. 조작 표면이 그대로 열린다.
    - 클라이언트는 **의도(입력)** 를 보내고 서버가 결과 상태를 계산한다. 델타 값 자체도 서버가 검증한다.
    - 반대 방향(서버 → 클라 이벤트)은 서버가 권한을 가지므로 절대값 스냅샷을 보내도 된다.
    - 델타 방식의 귀결로 **인바운드 요청은 하나도 누락되면 안 된다.** 상세는 설계 가이드라인 7번.

### 비기능

10. TLS ON, OFF 기능을 지원한다.
    - 빌드 단계에서 TLS 종속성을 포함하거나 제거할 수 있다.
11. 소켓으로부터 데이터를 받아 서버 로직으로 전달하기까지 최대한 메모리 copy 횟수를 줄여야 한다.
    - 목표 범위는 **소켓 수신 버퍼 → Codec 입력까지 복사 0회**이다.
    - Codec이 payload를 사용자 타입으로 변환하는 시점의 복사는 사용자 선택 영역이다.
12. 대용량 데이터 접근 시 전체 로드와 불필요한 복사를 피한다.
    - `memory_mapped_file`은 **큰 데이터에 랜덤 접근이 필요할 때만** 선택적으로 사용한다.
    - 스냅샷처럼 sqlite로 충분한 것은 sqlite에 저장한다.
    - mmap 영역 접근은 페이지 폴트 시 동기 블로킹이므로 **Worker에서만** 수행한다.

## 설계 가이드라인

### 1. 디렉터리 구조

**파일 접두어는 `kiotty_`, 네임스페이스는 `kiotty` 로 고정한다.** 모든 소스·헤더 파일명에 접두어를 붙여
다른 프로젝트의 헤더와 겹쳐 잘못 include 되는 사고를 막는다. 인클루드 가드도 경로를 그대로 반영한다
(`KIOTTY_CORE_RING_BUFFER_H`).

- include
    - kiotty_game_server_engine.h
    1. 서버 핸들 생성 지원
    2. 서버 Configuration 지원
    3. Usecase 등록 인터페이스 지원
    4. 쉽게 게임 로직을 구현하기 위하여 repository/ datasource/에 있는 기능들 제공.
- implementation
    - core
        - kiotty_result.hpp # C++11 컴파일을 대비한 에러 핸들링 + 결과 클래스. Result<ErrorCode, Type> 형태로 구현
        - kiotty_holder.hpp # Holder<Base>. 다형 객체를 힙 없이 담는다. unique_ptr 을 대신한다
        - kiotty_ring_buffer.hpp # 고정 용량 FIFO. 용량은 생성자에서 정해지고 이후 늘지 않는다
        - kiotty_bytes.hpp # Bytes(참조 카운트 블록), ByteView(남의 버퍼를 가리키는 읽기 전용 조각)
        - kiotty_connection_buffer.hpp # ReceiveBuffer, SendBuffer 와 그 항목 타입. Connection 하나가 쓰는 두 버퍼
        - kiotty_connection_info.hpp # ConnectionInfo. 커넥션이 무엇인지. 소켓 타입을 끌고 오지 않는 POD
        - kiotty_state_stream.hpp # IStateStream, IStateSink, IMutableStateStream, MutableStateStream
          # 밖으로 나가는 길도 이것을 쓴다. Connection 이 IStateSink<OutgoingPacket> 을 구현한다
        - kiotty_sequence_state_stream.hpp # SequenceStateStream, SequenceStateSink. state_sequence 순서로만 반영한다

    - presentation/

        - socket/ # socket에 대한 크로스 플랫폼 인터페이스 제공
            - Socket
            - TlsSocket
            - backend/

                - kiotty_linux_socket.cpp
            - tls_backend/ # 기존 backend의 함수를 활용하여 TLS 기능을 구현함
                - kiotty_windows_tls_socket.cpp
                - kiotty_linux_tls_socket.cpp
        - connection/
            - Connection # 커넥션 하나. 자기 수신 버퍼와 송신 버퍼를 소유한다. IStateSink<OutgoingPacket> 을 구현한다

        - io_loop/

              # 백엔드별로 갈리지 프로토콜별로 갈리지 않는다. UDP 도 같은 IoLoop 에 등록된다
            - backend/
                - iocp
                - io_uring
                - epoll
        - codec/ # payload <-> 사용자 파라미터 번역. 소유 경계는 미결정
    - domain/
        entity/
            - packet <-> entity 직렬화 기능 제공
        usecase/
            - IUsecase # 사용자가 채운다. 반드시 Session Repository를 종속성으로 가진다
            - IPublicUsecase # 인증 예외. 로그인, 버전 확인 등
            - UsecaseRegistry # command -> Usecase 매핑 보유
        worker/
            - IWorker # Worker Thread. 사용자가 실행되는 로직을 정의할 수 있음. 개수와 용도는 사용자가 정한다
            - WorkerRegistry # 서버 핸들이 소유. Usecase가 여기서 필요한 Worker를 주입받는다
    - repository/ # 사용자가 게임 로직은 만드나 범용적으로 사용하는 로직들은 제공함.
        - cryptor/
            - PasswordHasher # 비밀번호 단방향 해시. 복호화 함수가 존재하지 않는다
            - Cryptor # 세션 토큰·저장 데이터의 양방향 암복호화. AES256
        - session/ # 로그인, 로그아웃을 통해 세션을 만드는 기능. 패킷을 해석하여 세션을 찾는 기능. 세션 인증. 고아 세션 재바인딩
        - history/ # 데이터 복구 및 부인방지를 위한 히스토리를 쌓은 기능. 쌓인 히스토리를 compact하여 snapshot으로 남기는 기능. App 전체 State를 snapshot으로 복구하는 기능 제공
    - datasource/ # 인터페이스는 전부 동기(블로킹)다. 따라서 Worker에서만 호출한다
        - in_memory/
        - sqlite/ # WAL 모드 사용. writer는 단일이므로 쓰기는 자동 직렬화된다

**`cryptor/` 를 둘로 나눈 이유.** 비밀번호는 되돌릴 필요가 없다. 되돌릴 수 있는 형태로 보관하면 저장소가
새는 순간 평문과 같아진다. `PasswordHasher` 에는 **복호화 함수를 두지 않는다** — 없는 함수는 잘못 쓸 수 없다.
양방향 암복호화가 정말 필요한 것(세션 토큰 보관, 저장 데이터)만 `Cryptor` 가 맡는다.

### 2. 패킷 처리 흐름

1. IoLoop가 헤더 24 byte를 읽고 검증한다. (MAGIC, version, payload_length 상한)
2. IoLoop가 `payload_length`만큼 payload를 읽는다.
3. IoLoop가 이 패킷에 **`state_sequence`** 를 부여한다.
    - 세션별 수신 순서 번호다. TCP가 순서를 보장하므로 이 시점의 번호는 항상 정확하다.
    - 헤더의 `correlation_id`와는 다른 것이다. 서버 내부용이며 와이어에 나가지 않는다.
4. **Codec**이 사용자가 정의한 번역 로직을 실행하여 `command`와 파라미터를 추출한다.
    - 이 시점 이후 payload 버퍼는 반납할 수 있다.
5. **UsecaseRegistry**에서 `command`로 Usecase를 찾는다.
6. `IPublicUsecase`가 아니면 **엔진이 먼저 세션 인증을 검사한다.** 실패하면 Usecase에 도달하지 않는다.
7. `Usecase.execute(parameters, state_sequence)`를 호출한다.
    - Usecase는 **생성 시점에** 자신이 필요로 하는 Repository와 Worker를 주입받아 이미 들고 있다.
    - 의존성 주입은 사용자가 Usecase를 정의할 때 수행한다.
8. Usecase는 자신의 로직을 직접 수행하거나, 주입받은 Worker에 로직을 넘겨 실행을 위임한다.
9. IoLoop는 7번이 반환되는 즉시 다음 수신으로 돌아간다. **Worker 완료를 기다리지 않는다.**
10. 작업 결과는 inline이든 Worker든 **같은 경로**로 나간다. 세션의 sink에 흘리면 된다.
    sink 항목에는 그것이 응답인지 이벤트인지가 붙어 있어야 한다. 헤더 생성 규칙이 다르기 때문이다.

    | | correlation_id | DropPolicy |
    | --- | --- | --- |
    | 응답 | 요청 값을 **반사** | `Never` |
    | 이벤트 | 세션별 **다음 시퀀스** 발급 | `Oldest` |

### 3. ConnectionState의 정의

```cpp
// Connection가 수신/송신 방향의 상태를 각각 하나씩 가진다.
// 실행 도메인은 상태가 아니다. command -> Usecase -> Worker 경로로 서버가 결정한다.

enum class RecvStep
{
    ReadingHeader,  // 헤더 24byte가 모일 때까지 누적
    ReadingPayload, // payload_length만큼 모일 때까지 누적
    Dispatching,    // 패킷 1개 완성. Codec -> Registry -> Usecase 호출 (머무는 시간 0)
};
// AwaitingWorker는 없다. Codec이 payload를 파라미터로 변환한 뒤 payload 버퍼가 해제되고,
// Usecase.execute()가 즉시 반환하므로 수신이 Worker를 기다리지 않는다.

enum class SendState
{
    Idle,    // 보낼 것이 없어 체인이 멈춤. 큐에 넣은 생산자가 시동을 건다
    Sending, // 전송 진행 중. 다른 스레드는 전송을 발행하면 안 된다
};

enum class LifeState
{
    Active,
    Closing, // 새 작업 발행 금지. pending io가 0이 될 때까지 해제 대기
    Closed,
};

enum class DropPolicy // 송신 큐 항목마다 붙는다. 커넥션이 아니라 패킷의 성질
{
    Never,  // 응답, 영속 상태 변경. 큐 상한 초과 시 연결 종료
    Oldest, // 실시간 상태 이벤트. 오래된 것부터 버린다
};
```

### 4. 상태 전이 규칙

- 다음 수신 작업은 `Dispatching`으로 넘어가기 **전에** 발행한다. 로직 처리를 기다렸다 걸면
  그 시간만큼 수신 윈도우가 비어 요구사항 2번, 4번을 못 지킨다.
- 소켓당 발행된 수신/송신 작업은 각각 최대 1개. 단 수신 1개와 송신 1개는 **동시에 존재해도 된다.**
- `SendState` 전이 순서 (lost wakeup 방지): 생산자는 큐에 push를 **먼저** 하고 `Idle -> Sending` CAS.
  완료 핸들러는 `Sending -> Idle`로 **먼저** 되돌리고 큐를 한 번 더 확인한다.
- sink 콜백은 **직접 소켓에 쓰지 않는다.** `queue.push()` 후 `Connection.requestSend()`를 부르는 것이 전부다.
  직접 쓰면 다른 스레드가 진행 중인 전송과 겹쳐 같은 소켓에 송신이 2개 발행된다.
- `IStateSink::emit()`은 **절대 블로킹하지 않는다.** 큐 상한에 닿으면 `DropPolicy`에 따라
  버리거나 연결을 끊고 즉시 반환한다. 여기서 기다리면 호출한 스레드가 멈춘다.
  world worker면 시뮬레이션 전체가, inline이면 IoLoop 스레드가 멈춰 다른 세션까지 같이 막힌다.

### 5. 와이어 구조체 제약 (`core/packet_concept.hpp`)

- 헤더의 모든 필드는 `LittleEndian<T>`로 선언한다. 원시 바이트를 private으로 감춰
  **변환을 거치지 않고 필드를 읽는 방법이 존재하지 않게** 만든다.
- 그 결과 구조체의 정렬 요구가 1이 되어, 수신 버퍼의 임의 위치를 `const PacketHeader*`로
  캐스팅해도 **미정렬 접근 UB가 없다.** 요구사항 11번을 안전하게 달성하는 수단이다.
- `WireStruct<T, N>`를 상속하여 `sizeof(T) == N`과 standard layout 여부를 컴파일 타임에 검사한다.
- 와이어 구조체에 `bool`, `enum`, 포인터, `size_t` 사용 금지. 플랫폼마다 크기가 다르다.

### 6. 송신 발행 경로 (`Connection.requestSend()`)

백엔드마다 "누가 실제로 소켓에 쓰는가"가 다르다. 그 차이를 메서드 하나 뒤로 숨긴다.
호출하는 쪽은 어느 백엔드든 `queue.push()` → `requestSend()` 두 줄로 동일하고,
`SendState`의 `Idle`/`Sending` 정의도 동일하다.

| | 실제 쓰기 주체 | 깨우기 수단 | 이유 |
| --- | --- | --- | --- |
| IOCP | **아무 스레드나** | 필요 없음 | 작업이 발행 시점에 자기완결적이고, 소켓이 스레드가 아니라 포트에 등록된다 |
| epoll | `send()` 는 **루프 스레드만** | `epoll_ctl` 로 `EPOLLOUT` arm | `epoll_ctl` 자체는 스레드 안전하고, **준비된 이벤트를 추가하면 블록된 `epoll_wait` 를 그 자리에서 깨운다.** 따로 깨울 필요가 없다 |
| io_uring | ring 소유 스레드 | `msg_ring` 또는 eventfd poll | SQ ring이 스레드 안전하지 않다 |

- **IOCP** : CAS에 이긴 스레드가 큐에서 꺼내 그 자리에서 `WSASend`를 발행한다. inline Usecase면
  IoLoop 스레드가 발행하게 되는데 **이것이 최적이다.** 스레드 홉이 0이다.
  발행 스레드를 옮기고 싶을 때만(예: world 틱 스레드의 브로드캐스트) `PostQueuedCompletionStatus`로
  포트에 가짜 완료를 던져 IOCP 워커에게 넘긴다. eventfd의 대응물이며 **필수가 아니라 선택이다.**
- **io_uring** : **IO 스레드마다 ring 하나 + 세션을 ring에 고정**한다. 그러면 제출이 ring당 단일 스레드가 되어
  락이 사라지고 구조가 epoll 모델과 같아진다. `IORING_SETUP_SQPOLL`은 8명 규모에서는 켤 필요 없다.

### 7. 순서 보장 상태 (`core/sequence_state_stream.hpp`)

요구사항 9번(델타만 허용)의 귀결로 **모든 인바운드 요청이 빠짐없이, 순서대로 반영되어야 한다.**
델타는 하나만 건너뛰어도 상태가 영구히 어긋나고, 절대값 대입과 달리 뒤늦게 복구되지 않는다.

역전이 생기는 지점은 하나뿐이다. `state_sequence` 자체는 IoLoop가 수신 순서대로 매기므로 항상 정확하지만,
**11번이 Worker A로, 12번이 Worker B로 가서 B가 먼저 끝나면** 반영 순서가 뒤집힌다.
다만 11번이 유실되는 것은 아니고 늦을 뿐이다.

- `SequenceStateSink.set(state_sequence, delta)` — 값을 넣을 때 **반드시 번호를 같이 넣는다.**
- `SequenceStateStream`은 머리부터 연속으로 채워진 것만 순서대로 반영하고 멈춘다.
- **슬롯 예약** : IoLoop가 번호를 부여하는 시점(패킷 처리 흐름 3번)에 슬롯을 pending으로 등록한다.
    - "11이 올지 안 올지 모르는 대기"가 "등록된 11번 슬롯이 아직 안 찼다"로 바뀐다. 타임아웃 판단이 명확해진다.
    - 버퍼 크기가 세션당 in-flight 요청 수로 자동 한정된다.
    - Usecase가 실패/취소하면 슬롯을 skip으로 표시해 머리가 지나가게 한다.
    - 워커가 죽어 슬롯이 영영 안 차는 경우만 타임아웃으로 처리한다. 델타는 건너뛸 수 없으므로
      **조용한 skip이 아니라 세션 오류로 취급하고 스냅샷 재동기화를 유도한다.**

**세션당 순서 보장 자체는 엔진 사용자 책임이다.** 어떤 Worker를 쓸지가 Usecase 소유이기 때문이다.
엔진은 `state_sequence`와 위 모듈이라는 재료만 제공한다. 사용자가 지켜야 할 계약은 다음과 같다.

> 서로 다른 Worker로 갈 수 있는 상태 변경 연산은, Repository의 임계 구역 안에서 자기 사전조건을 검사한다.
> Repository의 락은 **원자성**을 보장할 뿐 **순서**를 보장하지 않는다. 검사 없이 항상 성공하는 연산(누산, 대입)이나
> 여러 Repository에 걸친 불변식은 `SequenceStateStream`으로 직렬화하거나 사용자가 따로 처리해야 한다.

### 8. inline Usecase 가이드

Usecase가 Worker에 위임하지 않으면 **IoLoop 스레드에서 그대로 실행된다.** 지연이 가장 낮은 경로다.
다만 datasource 인터페이스는 전부 동기(블로킹)이므로, datasource를 타는 Repository를 inline에서 호출하면
**IoLoop 스레드가 디스크에서 멈추고 그 스레드가 담당하는 모든 세션이 같이 멈춘다.**

엔진은 이것을 막지 않는다. 함수가 얼마나 걸리는지는 사용자가 측정할 문제이므로 가이드만 둔다.

- inline : 메모리 조회, 계산, 캐시 조회 등 **측정으로 확인된 짧은 작업**
- Worker : datasource 접근, 파일 I/O, mmap 영역 접근, 그 외 시간이 보장되지 않는 모든 작업

### 9. 클라이언트 수신 구조

클라이언트는 구현 범위 밖이지만, **프로토콜이 클라이언트를 구현 가능하게 만들어야 하므로** 전제하는 구조를 적는다.
서버가 응답과 이벤트를 같은 소켓으로 보내기 때문에 클라이언트는 이 둘을 스스로 갈라야 한다.

**요청을 동기 함수로 쓰고 싶다면 수신 스레드는 필수다.** 요청을 보낸 스레드가 직접 소켓을 읽으면,
그 자리에 도착하는 것이 자기 응답이라는 보장이 없다. 이벤트가 먼저 도착하면 그것을 처리하느라 응답이 늦어지거나,
버리면 이벤트가 유실된다.

```
수신 스레드 1개
   │  헤더 24byte를 읽는다
   ▼
flags.Event 비트를 본다
   ├── 0 (응답) ──► correlation_id 로 대기 중인 요청을 찾아 깨운다
   │                 └─ sendRequest() 를 부른 스레드가 그 자리에서 반환된다
   └── 1 (이벤트) ─► 이벤트 큐에 넣는다
                     └─ waitEvent() 로 꺼내가거나, 콜백 스레드가 꺼내 콜백을 부른다
```

- **응답은 큐가 아니라 `correlation_id → 대기 슬롯` 표로 받는다.** 큐로 받으면 여러 요청이 동시에 떠 있을 때
  자기 것이 아닌 응답을 꺼내게 된다. 슬롯이면 각 요청 스레드가 자기 것만 골라 깨어난다.
- **이벤트 콜백을 수신 스레드에서 직접 부르지 않는다.** 콜백이 오래 걸리면 그동안 응답 처리까지 멈춘다.
  큐에 넣고 별도 스레드가 꺼내 부른다.
- `sendRequest()`에는 **타임아웃이 필요하다.** 연결이 끊기면 응답이 영영 오지 않는다(서버는 재전송하지 않는다 — S8).

### 10. 분할 패킷 조립

64 KiB를 넘는 데이터는 `flags`의 분할 비트로 조각내어 보낸다. **조각을 모으는 일은 사용자 정의 Repository가 한다.**
엔진은 조각을 그대로 Usecase에 올리고, Usecase는 받은 조각을 Repository에 계속 넘긴다. 완성 여부를 아는 것도
완성본을 돌려주는 것도 Repository다.

```
IoLoop ──► Codec ──► Usecase ──조각──► Repository
                        ▲                  │
                        └── 완성본 또는 ────┘
                            "아직 덜 왔다"
```

엔진이 조립하지 않는 이유는 하나다 — **완성본을 어디에 얼마나 담아 둘지가 게임마다 다르다.** 엔진이 조립하려면
세션마다 미완성 버퍼를 들고 있어야 하는데, 그 상한과 만료 정책이 곧 게임 설계다.

사용자가 지켜야 할 것.

- `execute()`가 반환되면 payload 뷰는 무효가 된다. **Repository는 조각을 자기 저장소로 복사해서** 들고 있어야 한다.
- 미완성 조각의 **개수 상한과 만료 시간을 반드시 둔다.** 두지 않으면 마지막 조각을 안 보내는 것만으로 메모리가 샌다.
- 조각들은 같은 `command`로 오고, `LastFragment` 비트가 선 조각이 마지막이다.

## 범위 밖 / 이후 계획

- **heartbeat** : 클라이언트가 구현 범위 밖이므로 도입하지 않는다.
  - 알려진 한계 : 무선 단절처럼 아무 신호 없이 끊기는 경우 TCP 재전송 타임아웃까지 감지되지 않는다.
    정상 종료(FIN)와 크래시(RST)는 즉시 감지된다.
- **rate limiting** : future plan. 도입 전까지 요구사항 4번은 "정상 클라이언트 전제"에서만 만족한다.
- **UDP** : 1차 범위 밖. 다만 **전용 루프를 따로 두지 않는다.** `IoLoop`는 백엔드별로 갈리지 프로토콜별로
  갈리지 않으므로, UDP 소켓도 같은 `IoLoop`에 등록되고 완료 처리만 달라진다.
- **repository 추가분** : room, cache, metrics, clock. 아래 미결정 사항이 정리된 뒤 착수한다.
- **클라이언트 코드 작성 가이드** (`docs/client_guide.md`) : **설계가 모두 확정된 뒤에 만든다.**
  서버는 이 엔진 위에 게임 로직을 얹어 만들고, 클라이언트는 그 서버와 통신하는 코드를 이 가이드를 보고
  생성한다. 생성된 코드는 클라이언트가 지금 쓰고 있는 MockServer를 그대로 대체한다.

  가이드가 반드시 담아야 할 것.

    1. **Usecase 목록을 그대로 나열한다.** command 번호, 요청·응답 payload 구조, 실패 코드까지.
       이 목록이 곧 클라이언트가 만들 함수 목록이다.
    2. 요청은 **동기 함수** 형태로 쓸 수 있어야 한다.

        ```cpp
        Response doUsecase(Client& client, const Request& request);
        ```

    3. 이벤트는 **스트림** 형태로 받는다. `Client`를 종속성으로 받아 만든다.

        ```cpp
        Stream<GameEvent> game_event_stream(client);
        ```

    4. 이 둘이 한 소켓에서 갈라지는 방법 — 수신 스레드, `flags`의 `Event` 비트, `correlation_id` 대기 슬롯,
       타임아웃. 설계 가이드라인 9번이 그 바탕이다.
    5. 재연결 절차 — 세션 토큰 보관, 재바인딩 요청, 재바인딩 후 스냅샷 조회. 세션 유스케이스 S10~S12가 그 바탕이다.

## 미결정 사항

1. **브로드캐스트 대상 결정** — world Worker가 어떤 세션 집합에 흘릴지 정하는 방법.
   세션 수명(끊긴 세션에 emit하는 경우)과 직렬화 1회 + 참조 카운트 블록 공유 방식 포함.
   sink 콜백이 무엇을 하는지는 설계 가이드라인 4번, 6번에서 확정되었다.
2. **Codec의 소유 경계** — 엔진이 제공하는 범위와 사용자가 정의하는 범위의 구분.
3. **Worker 인터페이스 상세** — 스레드 생성, 비동기 완료 통지, 취소/타임아웃.
   설계 가이드라인 7번의 슬롯 타임아웃이 여기에 딸려 있다.
4. **room** — 서로 연관된 세션 집합에 대한 정보와 접근. 1~3번이 정리된 뒤 정의한다.
5. **요구사항 4번의 측정 조건** — 평균/최대/p99 중 무엇인지, 어떤 부하에서인지.
6. **응답 유실 시 재요청 처리** (세션 유스케이스 S8) — 요청은 반영되었는데 응답만 유실된 경우,
   클라이언트가 재요청하면 델타가 두 번 적용된다. 커넥션당 `correlation_id`로 중복을 억제할지,
   재요청을 금지하고 스냅샷 재동기화만 허용할지 정해야 한다.
