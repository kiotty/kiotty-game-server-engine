# 개념 관리 프로토콜

`code-inspector`, `cpp-developer`, `cpp-tester` 가 **공동으로 지키는** 규약이다. 세 역할이
개념을 각자 다르게 다루면 한쪽이 들여온 개념을 다른 쪽이 지우는 일이 생긴다.

---

# 1. 왜 — 개념에는 예산이 있다

코드를 읽는 비용에서 가장 큰 항목은 문법이나 줄 수가 아니라 **처음 보는 개념의 수**다.
개념 하나는 코드 밖에서 배워야 하고, 배운 뒤에도 "이 코드에서 이 개념이 정확히 어디까지
적용되는가"를 다시 따져야 한다.

**설계 문서에 있는 개념은 이미 값을 치른 개념이다.** 사용자가 그 문서를 쓰거나 읽으면서
한 번 배웠다. 반면 구현하다가 슬쩍 들어온 개념은 아무도 값을 치르지 않았고, 나중에 코드를
읽는 사람이 전액을 낸다.

그래서 원칙은 하나다 — **설계 문서에 있는 개념으로 해결되면 새 개념을 들이지 않는다.**
들여야 한다면 **값을 치르게 한다** (§3 의 학습 확인). 이미 들어와 있는데 값을 안 치른
개념은 **없앨 수 있는지 먼저 본다**.


# 3. 새 개념을 만났을 때

## 3.1 먼저 판정한다 — 정말 새 개념인가

아래를 거친 뒤에도 대장에 없으면 새 개념이다.

1. `concepts` 에 있는가? (다른 표기·다른 언어 규약 표기일 수 있다 — §3.2)
2. `design_docs` 의 문서에 있는가? `defines` 만 믿지 말고 **문서를 grep** 한다.
3. 그 분야의 표준 용어인가? (`fbo`, `vao`, `dpi`, `rgba` — 이건 개념 추가가 아니다)
4. 언어·표준 라이브러리의 기본 기능인가? (`unique_ptr`, `IDisposable`, `suspend` —
   이건 개념 추가가 아니다)

**3·4번을 넓게 잡지 않는다.** "GL 하는 사람은 다 안다"로 넘기면 학습 확인이 무의미해진다.
사용자가 그 개념을 쓰는 코드를 직접 쓴 적이 있는지가 실질적인 기준이고, 그건
`user_profile.md`(§5)를 보면 안다.

## 3.2 같은 것을 두 이름으로 부르지 않는다

**같은 기능을 가리키는 서로 다른 용어는 그 자체로 새 개념이다.** 읽는 사람은 두 이름이
같은 것인지 다른 것인지 확인해야 하고, 그 확인 비용이 진짜 새 개념보다 더 크다.

찾는 방법: 대장의 `name` 과 `avoid` 를 놓고 코드를 grep 한다. 언어 규약에 따른 표기 차이
(`setViewport` / `SetViewport` / `pgo_view_set_viewport`)는 **같은 이름으로 센다.**

```
대장:  RenderTarget  (= 서피스)   avoid: ["Surface", "Canvas", "DrawBuffer"]
코드:  OverlayRenderTarget ✓ / SurfaceHolder ✗ / _canvas ✗
```

동의어를 찾으면 **대장의 `name` 쪽으로 통일한다.** 어느 쪽이 정식인지 대장에 없으면
사용자에게 묻는다. **다수결로 정하지 않는다** — 잘못된 이름이 더 많이 퍼져 있는 경우가
흔하다.

## 3.3 역할별 조치 — 도입하는 쪽과 검수하는 쪽이 다르다

| 역할 | 상황 | 조치 |
| --- | --- | --- |
| `cpp-developer` | 구현에 새 개념을 **도입해야 한다** | §3.4 학습 확인 → 진행 → 대장 등재 |
| `cpp-tester` | 테스트·헬퍼에 새 개념을 **도입해야 한다** | §3.4 학습 확인 → 진행 → 대장 등재 |
| `code-inspector` | 코드에 **이미 있는데** 대장·문서에 없다 | §3.5 익숙함 확인 → 없앨 방법 검토 |

**비대칭인 이유.** 도입 시점의 개념은 필요해서 들어온다. 그러니 값을 치르게 하고(학습)
통과시킨다. 검수 시점의 개념은 **필요 없이 들어왔을 가능성**이 있다. 그러니 먼저 없앨
방법을 본다. 없앨 수 없다고 확인되면 그때 학습 대상으로 승격시킨다.

## 3.4 도입할 때 — 학습이 필요한지 반드시 묻는다 (developer / tester)

**새 개념을 코드에 넣기 전에** 사용자에게 묻는다. 넣고 나서 묻지 않는다 — 이미 들어간
개념을 되돌리는 건 비싸고, 그래서 아무도 안 되돌린다.

`AskUserQuestion` 으로 묻고, **질문에 개념을 한 문장으로 요약해 붙인다.** 이름만 던지면
사용자가 답할 수 없다.

```
`double buffering`(그리는 버퍼와 화면에 보이는 버퍼를 따로 두고 번갈아 바꾸는 방식)을
스텝 펌프에 도입해야 합니다. 이 개념이 익숙하십니까?
  1. 익숙하다 — 설명 없이 진행
  2. 대략 안다 — 간략한 설명을 듣고 진행
  3. 모른다 — 학습 문서를 만들어 주세요
```

답변별 조치.

**1. 익숙하다** → 설명하지 않고 진행한다. 아는 것을 설명하는 건 시간 낭비다.
`user_profile.md` 에 `익숙` 으로 기록한다.

**2. 대략 안다** → **간략히** 설명한다. 5~10줄, 이 코드에서 쓰이는 범위만. 개념 전반을
강의하지 않는다. 설명은 **대화로** 하고 문서를 만들지 않는다. 그리고 **그 요약을 코드
주석으로 남긴다** — 다음에 읽는 사람이 같은 질문을 하게 된다.

**3. 모른다** → §4 의 규약으로 학습 문서를 만든다. **문서를 만들고 끝내지 않는다.**
사용자가 이해했다고 할 때까지가 이 단계다.

```
문서 작성 → 사용자에게 읽어 보라고 요청 → 막히는 지점을 되묻게 함
  → 그 지점을 문서에 보강 → 사용자가 "이해했다" 고 할 때까지 반복
```

**반복 중에 코드 작업을 진행하지 않는다.** 이해되지 않은 개념 위에 얹은 코드는 사용자가
읽을 수 없고, 읽을 수 없는 코드는 유지할 수 없다.

**학습 요구가 한 작업에서 3개를 넘으면 멈추고 보고한다.** 그건 개념을 하나 들이는
문제가 아니라 **설계 접근이 사용자의 맥락과 어긋난 것**이다. 더 익숙한 개념으로 같은
일을 할 수 있는지 다시 본다.

## 3.5 검수할 때 — 없앨 수 있는지 먼저 본다 (inspector)

대장·설계 문서에 없는 개념을 코드에서 찾으면, 사용자에게 익숙한지 묻는다.

**익숙하다고 답하면** 그대로 두고, **대장 `concepts` 에 등재를 제안**한다. 익숙하다는
답은 "값을 이미 치렀다"는 뜻이므로 대장에 올려 다음 세션이 다시 묻지 않게 한다.
(`unregistered` 의 `status` 를 `user-familiar` → 승인되면 `promoted` 로.)

**익숙하지 않거나 잘 모르겠다고 답하면 없앨 방법을 찾는다.** 아래 순서로 검토한다.

1. **대장의 기존 개념으로 대체되는가.** 가장 좋은 결말이다. 새 개념이 기존 개념의
   특수한 경우일 때가 많다.
2. **그 개념을 담은 계층 자체가 필요 없는가.** 개념은 대개 계층과 함께 들어온다.
   경로 검수(`code-inspector` 의 경로 검수 절)와 같은 문제인 경우가 흔하다.
3. **이름만 바꾸면 개념이 사라지는가.** 이름이 개념을 불러온 경우다 —
   `SnapshotArbiter` 를 `pickNewestFrame()` 으로 바꾸면 개념이 아니라 함수가 된다.
4. **개념은 남기고 노출 범위를 좁힐 수 있는가.** 한 `.cpp` 안의 static 함수로 가두면,
   그 파일을 읽을 때만 값을 치른다.
5. **없앨 수 없다.** 그러면 §3.4 의 학습 대상으로 올리고, 대장에 등재하고,
   **왜 필요한지를 코드 주석과 대장 `note` 양쪽에 남긴다.**

1~4 는 전부 **제안이고 컨펌 대상**이다. 개념을 없애는 변경은 구조 변경이므로 혼자
결정하지 않는다.
